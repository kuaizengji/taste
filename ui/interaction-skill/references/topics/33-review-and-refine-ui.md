# 网页视觉评审与定向修改

> 按需参考 · 主题 33。用于页面已经能用，但主次不清、操作不顺，或每次让 AI 优化都会改坏满意部分的情况。把问题定位到具体位置，再限定修改、沿原路复查。

## 根据请求确定当前角色

- **只读评审**：用户说“看看问题”或“给建议”，只检查与提出建议。
- **执行修改**：用户要求修复或已经接受具体改动，直接在该范围内实施，不再次索要同一授权。
- **重新验证**：用户要检查结果，沿修改前的浏览路径验证，记录证据限制。

这些可以在同一会话中完成。独立评审确实有帮助且环境提供子智能体时，可以使用已获授权的委派机制；不能假装已有另一个 AI 参与，也不因本参考擅自创建新聊天或外发资料。

## 建立一个可比较的基线

先用项目已有说明确认页面服务谁、希望访客先做什么。摄影站可以优先看作品，后台可能优先处理待办；例子不是所有页面的统一目标。只询问会影响判断、且现有资料回答不了的问题。

具备浏览器能力时，实际走一条相关路径，例如“首页 → 作品详情 → 下一组 → 返回”，记录位置、动作和结果。真实购买、付款、发消息等有外部影响的动作不作为默认测试步骤。只有截图或代码时，明确分析依据，不写“已经操作通过”。

执行修改前通过已有版本或本轮补丁保留可恢复的差异；遵循项目 Git 规则，不擅自新建分支、强制重置或覆盖未提交工作。

## 给出可以选择的问题

首轮优先少量最影响主任务的问题；一两项通常易于判断，但不能为了数量限制隐瞒真实阻塞。每项按这个顺序描述：

**位置与状态 → 实际观察 → 对主任务的影响 → 最小修改 → 复查方式。**

分清功能/内容错误、任务层级建议和个人风格偏好。某种颜色、卡片或等权按钮不天然错误。没有证据的结论标为假设，没有发现问题时如实说，不为显得有用制造改动。

## 只改本轮接受的范围

复用现有组件、主题和素材。具体写明可以改的区域及需要保留的文案、图片、功能和风格；不把“让作品入口明显一点”扩成更换整站设计或技术栈。已经明确授权的同类修改可以继续，遇到实质超出范围再说明原因。

比较前后时保持同一内容、图片和数据，才能判断是否是布局与层级改善。实现了哪项改动就复查哪项，并检查它的直接关联行为：点击入口、内容切换、返回、焦点、窄屏等。局部视觉修改不自动触发全站重构或全面测试。

## 三段可复制请求

### 只读评审

> 这是【地址或页面资料】，用途是【用途】，希望访客先完成【主任务】。先不要修改代码，沿【起点 → 操作 → 返回】检查，优先给出影响任务的具体问题。每项写位置、观察、影响、最小建议和复查方式，区分风格偏好与功能问题。不能实际打开或操作时明确说明。

### 定向修改

> 本轮只处理【问题或编号】，允许修改【区域与状态】，保留【已满意的内容、素材、功能和风格】。先保留可恢复的本轮差异，沿用现有组件与样式约定，不重做其他页面。发现必须超出范围才能解决时先解释。完成后给出差异和复查结果。

### 沿原路复查

> 按修改前的【浏览路径】再次实际操作，确认原问题是否解决，并检查相关入口、内容、返回和切换。分别报告“已操作”“仅外观或代码检查”“尚未验证”。没有浏览器能力时给出我能执行的短清单，不把看过截图写成测试通过。

## 交付与回退

提供本轮改变及对应证据；截图与操作记录可以直接放在回复中，用户禁止落盘时不要另写文件。记录未验证的设备、浏览器和状态，不编造独立评审、日志或用户接受。

风格是否更合适仍由用户判断。用户要求回退时只撤回本轮指定差异，保护其他工作。代码检查、浏览器验证和用户最终认可分开说明。
